## 1. 需求拆解：产品答复把「一个问题」变成了「三个不变量 + 一个新风险」

产品答复引入 3 条规则：R1 转赠后原券**立即冻结**、原用户不可用；R2 仅指定接收人可领取；R3 24 小时未领取自动退回原账户。它们对应三个**互相独立**的技术保证：

| 编号 | 需要保证的事 | 唯一可靠实现位置 |
|---|---|---|
| I1 | 一张券**最多成功领取一次** | 数据库：唯一约束 / 单条条件更新 |
| I2 | 冻结期间**不可被消费**（含原用户、含并发消费） | 数据库：同一行的状态检查（消费路径也必须带状态条件） |
| I3 | 最终**恰好落到 {已领取, 已退回}** 之一（不能永久冻结） | 需要超时机制：DB 内部调度或延迟消息 |

关键推论一：**I1/I2 的正确性只能来自 MySQL，Redis 与队列都是"加速器"或"搬运工"，不是权威。** 因此 B、C 都不是 A 的替代方案，而是「A + 附加组件」。这条推论直接决定了推荐逻辑。

关键推论二：**R1 的「立即冻结」使「把冻结放进异步」不可接受**。C 若把冻结/领取整体异步化，会出现「用户看到已转赠、实际券还能被自己消费」的窗口——这是用户可见的资金级事故，不是技术瑕疵。所以 C 只能在「冻结与领取同步、后续副作用异步」这个约束下成立。

## 2. 三方案对比

### A. MySQL 条件更新（单库单行状态机）

核心写法（示意，**未编写也未运行**）：冻结 `UPDATE coupon SET status='FROZEN', receiver_id=?, frozen_at=NOW(), expire_at=NOW()+INTERVAL 24 HOUR WHERE id=? AND owner_id=? AND status='AVAILABLE'`；领取 `UPDATE ... SET status='CLAIMED', owner_id=? WHERE id=? AND status='FROZEN' AND receiver_id=? AND expire_at>NOW()`；判成功只看 **affected rows=1**，绝不 SELECT 后再 UPDATE。

- **适用业务**：单券争抢者≈1 人（正是本需求：指定接收人）、转赠属低频操作、有单库事务、团队无 Redis/MQ 运维能力或不愿引入第二故障域。
- **优点**：单一事实来源，无跨系统双写；行锁天然覆盖「领取 vs 超时退回」的竞争；失败恢复最简单（回滚/重试）；与发放记录、流水可同事务，审计友好；验收测试最便宜（2 线程抢同一行即可，见 P0-06 的四个场景）。
- **缺点**：所有写压力集中主库；24h 退回需要调度器（批量 `UPDATE ... WHERE status='FROZEN' AND expire_at<NOW()`）+ 建议叠加「读时惰性判定」兜底；失败原因（非本人/已过期/已被领）需二次查询才能给用户看得懂的提示；状态机非法流转要靠代码 + 表约束守住。
- **成本**：低。一张券表 + 状态列/约束 + 条件更新 + 一个定时任务 + 并发测试。无新中间件、无新运维面。
- **风险**：
  1. 调度器单实例或停摆 → 券**永久冻结**，用户表现为「我的券消失了」（R3 违约，且难被用户举证）；
  2. 经典读改写竞态（先查后更）→ 双领。必须用单条条件更新守死；
  3. 应用服务器时钟 → 过期判定漂移。必须用 DB `NOW()`，不用 JVM/Node 时间；
  4. 同事务内若再写流水/用户/风控多张表，锁顺序不一致会死锁；
  5. 将来分库分表 → 全表批量过期任务需按分片重写。

### B. Redis 协调 + MySQL（锁/令牌/热点状态前置）

Redis 用 `SET NX PX` 做领取令牌或状态缓存，命中成功后再落到 MySQL 条件更新；24h 可用 TTL 做展示与提前告警。

- **适用业务**：**一券多人抢**（例如改成"分享链接谁先点谁得"）、秒杀式热点、重试风暴打库、需要极快的重复请求拒绝。
- **优点**：把重复/无效请求挡在 DB 之前，保护主库；失败快、体验好；TTL 语义天然贴合 24h（仅作提示，不作真相）；可作为灰度/限流开关。
- **缺点**：双写一致性问题（Redis 说可领、DB 说不可领，或反之）；锁到期而事务未完 → 第二个请求进入（幸好 DB 条件仍能兜底，但说明**Redis 不减小正确性责任，只减小压力**）；Redis 故障时要决定 fail-open（退回 A，压力回灌主库）还是 fail-closed（业务停摆），这是必须提前拍板的策略；新增 key 设计、释放用 Lua 比较删除、监控与容量。
- **成本**：中高。Redis 集群/哨兵 + 客户端配置 + 降级开关 + key 生命周期 + 三类新测试（Redis 宕机、锁过期、主从切换）。
- **风险**：
  1. **最危险的一条**：把 Redis 当权威 → 一次 flush/故障切换就可能造成双领，且事后无法从 DB 复现；
  2. 若 24h 退回只靠 Redis TTL 实现，Redis 重启即丢失全部待退回券 → 批量资损；
  3. 本需求下争抢者≈1 人，收益极小、故障面变大 → 属于典型的**过度设计**。

### C. 异步队列 + MySQL

请求落库/投递消息，消费者改状态并做后续（通知、流水、退回）。

- **适用业务**：领取链路要串多个慢依赖（风控、外部权益核销、消息推送）、有明显流量尖峰、已具备 MQ 与幂等基建；**或仅用延迟消息承担 24h 自动退回**（这一半是合理且有价值的）。
- **优点**：削峰、解耦、天然重试与背压；延迟消息可替代轮询调度器实现 R3；后续副作用扩展成本低。
- **缺点**：与 R1「立即冻结」冲突——**冻结必须留在同步 DB 条件更新里**，否则出现双重消费窗口；领取变成最终一致，用户会看到「领取中」新状态，这是**新的业务规则，必须回 Gate 问产品**，不能由工程自行决定；至少一次投递 → 幂等键强制（否则重复领取/重复退回）；需要死信队列、重放工具、链路追踪；本地/CI 需要 MQ，验收从"断言状态"变成"断言最终状态"，测试更易 flaky，「未运行」风险上升。
- **成本**：高。MQ 集群 + 生产/消费 + 幂等表 + DLQ 运维 + 延迟消息特性（RocketMQ 延时级别 / RabbitMQ TTL+DLX）+ 约两倍代码路径。
- **风险**：
  1. 幂等写错 → 重复退回或重复领取（资损级）；
  2. 消息丢失/积压 → 券**永久冻结**或退回迟到数小时，且比 A 更难被发现（无行级痕迹）；
  3. 消费者若信任消息体而不重新按 DB 条件校验 → I1 破防；
  4. 排障从"看一行数据"变成"串三个系统"，P0-06 的故障恢复验收难度显著上升。

## 3. 推荐：**A（并在 A 内部用"批量过期任务 + 读时惰性判定"实现 R3）**

理由（业务语言，非技术偏好）：
1. 本需求的争抢强度是**每张券只有 1 个指定接收人**，B 要解决的"挤爆主库"根本不发生；C 要解决的"流量尖峰"在转赠场景也不存在。为不存在的问题付运维与一致性代价，是负收益。
2. 产品要求「**立即冻结**」，唯一能"立刻"并"唯一作数"的地方就是数据库那一行。B/C 都要在这条同步条件更新之上叠加，**它们不替代 A，只增加 A 之上的组件**。
3. B/C 引入的失效模式（锁过期、消息丢失）产生的后果恰好是本需求**最坏的用户结果**：券被领两次、或券永久冻结。A 的失效模式（调度器停摆）可通过"每实例可跑、幂等、带监控、读时兜底"压到最低，且可用一行 SQL 复核。
4. A 的验收证据最容易做到"可复现、可交给独立审查"，符合 P0-06/P0-07 对证据的要求。

**明确不做的事**：不因为"看起来更先进"而选 B/C；未获人类在 decision_gate 授权前，不得把实现悄悄换成 B/C（任务书 §2 明文要求）。

**重评触发条件（写入 ADR 的 `revisit_triggers`）**：
- 转赠规则改成"链接/群内谁先点谁得"（1 券 N 争抢者）→ 引入 B；
- 实测同券并发写冲突率或 p99 超标（阈值须先用压测定，不能拍数字）→ 引入 B 做前置挡板；
- 领取链路需要调用慢外部服务，或退回/通知需扇出多系统 → 对这些部分引入 C（冻结与领取仍留 A）；
- 24h 待退回体量大到批量 SQL 影响主库 → 过期机制迁到延迟消息（C 的局部使用）；
- 分库分表 → A 的批量过期任务按分片重写。
